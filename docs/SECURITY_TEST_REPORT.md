# Security Test Report

Scope: this application's own code and local/production-build test environment, at the commit this report was written against. No third-party infrastructure was tested (the Gemini API itself is Google's infrastructure — only this application's use of it was tested). This report distinguishes what was **actually executed** from what could not be verified — nothing below is marked PASS without having been run.

## NOT TESTED (with reason)

| ID | Item | Reason not tested |
|---|---|---|
| NT-001 | Exhaustive prompt-injection technique coverage against the live model | Only one adversarial payload/technique (direct instruction override + secret-disclosure request) was tested live (SEC-036), due to free-tier rate limits (10 RPM / 250 RPD on `gemini-3.6-flash`) making it impractical to burn quota testing every injection variant against the real API. The other 5 payload variants are verified at the application-wiring level only (mocked, SEC-016). A real model's behavior under a wider range of injection techniques (multi-turn, encoded payloads, etc.) is not exhaustively verified. |
| NT-002 | Real rate-limit (429) response specifically *from Gemini itself* (as opposed to the app's own limiter) | During live testing, the app's own in-memory rate limiter (10 requests/5min) was hit before enough real calls could be made in a short enough window to reliably trigger Gemini's own 10 RPM free-tier ceiling. The Gemini-side 429/quota-exhaustion error-mapping code path (both generic-rate-limit and quota-specific message variants) is verified against a mocked SDK (`tests/integration/gemini-provider.test.ts`) and was observed for real once already with the (now-replaced) OpenAI key's `insufficient_quota` response — confirming the general pattern (real 429 → safe mapped error) works, just not the Gemini-specific 429 text variant live. |
| NT-003 | Load/memory profiling under concurrent request volume | Only single-request latency was observed during development; no load-testing tool was run against this deployment. |
| NT-004 | Multi-instance / serverless rate-limit behavior under concurrent load | No multi-instance deployment exists to test against; documented as a known architectural limitation instead (see [SECURITY_ARCHITECTURE.md](SECURITY_ARCHITECTURE.md)). |
| NT-005 | Real screen-reader walkthrough of the live-rendered summary view | ARIA roles/labels verified by code review and structural testing; not exercised with actual assistive technology. |

## Explicitly not claimed

This report does not claim the application is "100% secure," "unhackable," or free of all possible vulnerabilities. It documents what was tested, how, and what the result was — see [PENETRATION_TEST_REPORT.md](PENETRATION_TEST_REPORT.md) for the corresponding narrative summary and residual risk statement.
