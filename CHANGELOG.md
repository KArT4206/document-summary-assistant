# Changelog

## Unreleased

### Added — Explicit, fail-safe production fallback gate (`OLLAMA_FALLBACK_ENABLED`)
- `src/lib/ai/ollama-provider.ts`: new `isFallbackEnabled()` — returns `true` only for the exact string `"true"`; unset, `"false"`, and any other value (including truthy-looking strings like `"1"`/`"yes"`) are treated as disabled. Not derived from `NODE_ENV` — enabling fallback is always an explicit, per-deployment configuration decision.
- `src/lib/ai/router.ts`: the gate is checked *before* `isOllamaAvailable()` is ever called, so when disabled the router makes zero network attempts toward `OLLAMA_BASE_URL` — not even the lightweight availability probe. Previously the router always attempted Ollama on a fallback-eligible Gemini failure; production deployments with no real Ollama server would still reach the (harmless but unnecessary) `isOllamaAvailable()` check. Now that path is skipped entirely, and a new `fallback=disabled` log field records that the skip happened.
- `.env.example`: `OLLAMA_FALLBACK_ENABLED=false` added as the documented default, with an extended comment explaining why `127.0.0.1` has no meaning in a deployed environment and why the flag defaults off.
- 13 new tests across `tests/integration/ai-router.test.ts` (+9, restructured into "fallback enabled" / "fallback disabled" describe blocks) and `tests/integration/ollama-provider.test.ts` (+4, for `isFallbackEnabled()` itself). Unit/integration total: 96 → 105.
- Documentation (README, ARCHITECTURE, SECURITY_ARCHITECTURE, PRIVACY_AND_DATA_HANDLING, THREAT_MODEL, APPROACH, SECURITY_TEST_REPORT) updated to distinguish Gemini (primary), Ollama (local-development fallback, opt-in), and optional private Ollama (production fallback, opt-in) — localhost Ollama is documented as a development convenience only, never a production deployment capability.

### Added — Ollama local-model fallback
- `src/lib/ai/ollama-provider.ts` (`OllamaProvider`): implements `AIProvider` against a local/private Ollama server's `/api/chat` endpoint (default `http://127.0.0.1:11434`, model `gemma4:e4b`). Same system prompt, same `<document>` untrusted-content delimiting, and the same `SummaryResultSchema` validation as `GeminiProvider` — structured output requested via a JSON Schema derived from that same Zod schema (`z.toJSONSchema`), so the "shape we ask for" and "shape we accept" can never drift apart. Includes `isOllamaAvailable()`, a fast bounded availability check used before attempting a full generation call.
- `src/lib/ai/router.ts` (`AIRouter`): the new active `AIProvider`. Gemini primary, Ollama fallback — but only for `AI_RATE_LIMITED` (immediate fallback) or `AI_TIMEOUT`/`AI_PROVIDER_ERROR` (one retry on Gemini, then fallback). Explicitly never falls back for `AI_CONFIG_ERROR` (would hide a permanently broken deployment) or `AI_INVALID_RESPONSE` (a data-quality problem, not an outage). Returns a single friendly `AI_UNAVAILABLE` error if Ollama is also unreachable/failing, with no internal detail (provider name, URL, stack trace) ever reaching the client. Logs safe structured events only (`provider=gemini status=... fallback=ollama`) — never document text, prompts, or keys.
- Two new `AppError` codes (`src/lib/errors.ts`): `AI_CONFIG_ERROR` (500 — permanent misconfiguration, distinct from transient `AI_PROVIDER_ERROR`) and `AI_UNAVAILABLE` (503 — both providers exhausted). `GeminiProvider`'s missing-key and 401/403 cases now map to `AI_CONFIG_ERROR` instead of the generic `AI_PROVIDER_ERROR`, so the router can tell "broken forever" apart from "broken right now."
- `.env.example` and local `.env.local` updated with `OLLAMA_BASE_URL`/`OLLAMA_MODEL` (no real secrets — Ollama needs no API key).
- 25 new tests: `tests/integration/ollama-provider.test.ts` (15, mocked `fetch`) and `tests/integration/ai-router.test.ts` (10, mocked providers) — the router's fallback/no-fallback decision tree is verified without spending any real Gemini quota, per explicit instruction. Unit/integration total: 71 → 96.
- UI unchanged: the response shape is identical regardless of which provider produced it, so `SummaryView` needed no changes.

### Added — Production deployment fixes (Vercel)
- Three real defects found during live Vercel deployment verification, invisible locally (dev and `next start` both resolve modules directly from `node_modules` rather than a pruned/traced serverless bundle): `@napi-rs/canvas`'s native `.node` binary and `pdfjs-dist`'s worker `.mjs` file were silently dropped from the deployed function (broke PDF extraction, raw 500s); `tesseract.js`'s worker-script tree plus several transitive dependencies (`bmp-js`, `idb-keyval`, `node-fetch`, etc.) were likewise dropped (broke OCR). Fixed via explicit `outputFileTracingIncludes` globs in `next.config.ts` — bundling `tesseract.js` instead was tried and made things worse (its dynamic `__dirname`-based requires don't survive bundling).
- Disabled the default `x-powered-by` header (`poweredByHeader: false`) — a minor framework-fingerprinting info disclosure found during the live security check.
- Verified against the real production deployment: PDF text extraction, image OCR, and scanned-PDF OCR all return real Gemini-generated summaries; security headers, rate limiting, path-traversal/spoofed-extension rejection all confirmed live.

### Changed
- **Switched the active AI provider from OpenAI to Google Gemini** (free tier, `gemini-3.6-flash`), to keep the project at zero API cost. The OpenAI implementation (`src/lib/ai/openai-provider.ts`) remains in the codebase, fully functional and tested, as a second implementation of the same `AIProvider` interface — proving the abstraction is real, not just a single hardcoded class. Switching back (or to another provider) means changing one line in `src/lib/ai/index.ts`.
- Narrowed `.gitignore`'s `.env*` pattern to `.env`, `.env.local`, `.env.*.local` — the previous blanket pattern was also hiding `.env.example` (the checked-in template) from git, which contributed to a real incident (see Fixed, below).

### Fixed
- **CSP breaking hydration**: an initial strict CSP (`script-src 'self' 'nonce' 'strict-dynamic'`) silently broke React hydration in the production build, because the nonce was only set on the response, not the request Next.js's App Router actually reads it from. Fixed by forwarding the CSP on the request headers too and forcing dynamic rendering so a per-request nonce is available at all.
- **Silent upload truncation on 10-15MB files**: discovered during security review that Next.js's own middleware/proxy layer has a default 10MB body-size cap (`proxyClientMaxBodySize`), silently truncating legitimate uploads under this app's advertised 15MB limit and surfacing as a generic 500 error. Fixed by raising the config value in `next.config.ts`; locked in with a permanent E2E regression test.
- **Corrupted-PDF handling gap**: an early refactor for scanned-PDF OCR support left `parser.getInfo()` outside the try/catch that wrapped `parser.getText()`, so a genuinely malformed PDF threw an uncaught `InvalidPDFException` instead of the intended `EXTRACTION_FAILED` error. Caught by an automated test, fixed immediately.
- **Gemini timeout error not mapped correctly**: the Gemini SDK throws a generic `AbortError` on client-side timeout, not an SDK-specific error with "timeout" in its message — the initial error mapping missed this and fell through to a generic `AI_PROVIDER_ERROR`. Discovered and fixed during live verification (forced a 1ms timeout against the real API, observed the actual error shape, fixed the mapping, reverted the test value).
- **Deprecated model reference**: the initially-configured `gemini-2.5-flash` turned out to already be unavailable to new projects — caught via a real 404 from the live API during verification (not from documentation, which was out of date), switched to `gemini-3.6-flash`.
- **Secret handling incident (caught before any exposure)**: a real API key was briefly pasted into `.env.example` (the checked-in template) instead of `.env.local`. Caught before any `git add`/commit; confirmed via `git log --all -p` that it never entered git history; moved to `.env.local`, `.env.example` restored to variable-names-only, and the `.gitignore` pattern that had been silently hiding `.env.example` from routine `git status` checks was narrowed (see Changed, above) so this class of mistake is easier to catch next time.

### Known limitations
- **Ollama fallback requires a real, privately-reachable Ollama server in production** — this codebase does not provision one, and `127.0.0.1` has no meaning inside a deployed serverless function. Without one, `isOllamaAvailable()` correctly reports unavailable and the app returns an honest `AI_UNAVAILABLE` message rather than a fabricated success. See `docs/SECURITY_ARCHITECTURE.md`.
- Rate limiting is in-memory and single-process; not effective across multiple serverless instances (documented, not silently accepted — see `docs/SECURITY_ARCHITECTURE.md`).
- Gemini free tier is low-volume (10 RPM / 250 RPD) — fine for this assessment, not for real production traffic without upgrading.
- The real Gemini happy path, including timeout/missing-key/invalid-key/provider-error and prompt-injection resistance, has been live-verified end-to-end (see `docs/SECURITY_TEST_REPORT.md`). Exhaustive coverage of every possible injection technique and a live-observed Gemini-specific 429 (as opposed to the app's own rate limiter) remain mocked-only, due to free-tier quota constraints on live testing.
